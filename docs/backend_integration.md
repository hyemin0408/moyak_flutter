# MOYAK 백엔드 연동 준비

현재 실제 API 주소·명세·통신 구현은 없다. 아래 서비스 메서드와 모델은 앱 내부의 제안된 계약이며 서버의 URL, HTTP 메서드, JSON 키를 정의하지 않는다.

## 현재 화면과 이동

| 화면 | 파일 | 이동 |
|---|---|---|
| 시작 | lib/main.dart | onStart 또는 Navigator.push → 홈 |
| 홈 | lib/screens/kiosk_menu_screen.dart | 첫 메뉴 → 의약외품, 둘째 → 앱 안내, 셋째 → 안내 메시지 |
| 의약외품 | lib/screens/kiosk_product_list_screen.dart | 검색·카테고리·예시 담기, pop → 홈 |
| 앱 안내 | lib/screens/kiosk_qr_download_screen.dart | 연동 버튼 → 기기 연동, pop → 홈 |
| 기기 연동 | lib/screens/kiosk_device_pairing_screen.dart | 임시 QR·대기 표시, pop → 앱 안내 |
| 인증 완료 예시 | lib/screens/kiosk_auth_complete_screen.dart | lib/preview_auth_complete.dart에서만 별도 실행 |

현재 이동 방식은 Navigator.push(MaterialPageRoute) / pop이며 그대로 유지한다. 인증 완료 이벤트·자동 화면 전환은 없다.

## 파일 경계

- screens/: Flutter UI, 입력 상태, 기존 화면 이동. 네트워크 요청을 직접 넣지 않는다.
- demo/demo_products.dart: Figma 재현용 데이터와 이미지 위치·표시 가격. 실제 재고나 판매 데이터가 아니다. 화면은 기존과 같은 자료를 읽는다.
- models/backend_models.dart: 기기, 연동 상태, 인증 상태, 회원, 제품, 재고, 장바구니, 구매에 대한 앱 내부 자료형. JSON 직렬화는 아직 없다.
- services/backend_services.dart: 기능별 비동기 서비스 계약.
- services/service_result.dart: 성공 값 또는 분류된 오류. null을 성공으로 해석하지 않는다.
- services/backend_service_container.dart: 향후 실제 어댑터를 외부에서 주입할 지점. 현재 모든 서비스는 미설정(null)이며 예시 서비스로 대체하지 않는다. 아직 화면에 주입하지 않는다.

## 기능별 연결 지점

| 기능 | 서비스 | 향후 연결 방식 |
|---|---|---|
| 기기 식별·연동 | KioskDeviceService | 기기 ID를 설정/플랫폼 저장소에서 읽고 연동 세션 시작·결과 조회 |
| 인증 결과 | IdentityService | 확인된 연동 세션에 대해 서버가 알려 준 인증 상태 확인 |
| 회원 | MemberService | 실제 인증 세션의 회원 표시 정보 조회 |
| 제품·재고 | CatalogService | 검색·분류 결과와 기기별 재고 조회 |
| 장바구니·구매 | PurchaseService | 서버 장바구니 갱신, 구매 요청 및 상태 확인 |

명세가 오면 필요한 범위부터 연결한다. 상태 관리는 현재 StatefulWidget/setState를 유지해도 된다. 화면별 생성자에 필요한 서비스만 전달하고 main.dart에서 실제 어댑터를 조립하면 된다. 지금은 화면의 예시 동작과 API 계약을 분리하는 단계이므로 런타임 서비스 연결은 없다.

## 실제 API 명세를 받은 뒤

1. 주소, 엔드포인트, 필수 요청 값, 응답 구조, 페이지 처리, 가격 단위, 재고 기준을 확인한다.
2. services/api/ 아래에 실제 HTTP 어댑터와 wire DTO를 추가한다. 서버 JSON과 앱 모델 사이 변환은 이 계층에서 수행한다. UI는 JSON 키를 알 필요가 없다.
3. 설정되지 않은 주소·기기 ID·인증 정보는 명시적 notConfigured 오류로 처리한다. 데모 데이터나 성공 상태로 자동 대체하지 않는다.
4. 오류는 network, timeout, unauthorized, forbidden, validation, conflict, invalidResponse 등으로 변환한다. 서버 응답 본문·토큰·개인정보를 UI 메시지나 로그에 그대로 출력하지 않는다.
5. HTTP 상태별 오류 매핑·타임아웃·취소·응답 검증은 실제 계약에 맞게 테스트한다. 화면은 로딩·오류·성공을 나누되 기존 레이아웃의 변경은 별도 작업으로 결정한다.
6. 구매 요청의 중복 방지·재시도 가능 여부·서버 가격/재고 재검증은 백엔드와 합의한다. 명세 없이 구매/결제를 자동 재시도하지 않는다.

서비스의 예상 실패는 ServiceFailure로 반환한다. 코드 버그까지 모두 unknown으로 삼켜서는 안 된다. 실패 후 인증 완료나 구매 완료 화면으로 이동하지 않는다.

## 예시 화면과 실제 인증의 구분

lib/demo/에는 실제 서비스 인터페이스를 구현하거나 인증/구매 성공을 반환하는 구현이 없다. 테스트용 어댑터가 필요하면 test/의 fake에 두고 실제 앱에 주입하지 않는다.

기기 화면의 MD-2409-ROME는 디자인 예시 문자열이지 실제 기기 식별자·비밀 키가 아니다. 인증 완료 화면의 지*민과 한도/로그아웃 문구도 정적 디자인 예시다. 실제 연동 성공 판정에 사용하면 안 된다.

장바구니의 최초 7,000원 선택은 Figma 예시를 재현한 로컬 상태다. 현재 담기와 합계 계산은 실제 구매를 처리하지 않는다. 실제 구매 모델의 합계는 서버 결과를 사용한다.

완료 화면으로 실제 이동하려면 서버의 연동 결과뿐 아니라 인증 상태와 회원 정보가 실제로 확인되어야 한다. 구체적인 판정 및 화면 전환 시점은 API 명세 확정 후 구현한다. 단순한 대기 시간 경과나 화면 버튼 클릭은 성공 이벤트가 아니다.

## 설정과 민감 정보

API 주소는 향후 배포 환경에서 설정하며 지금 기본 주소를 만들지 않는다. 클라이언트에 서버 비밀 키를 넣지 않는다. dart-define 값도 앱에 포함될 수 있으므로 비밀 저장소가 아니다.

토큰은 실제 인증 흐름이 정해진 후 안전한 플랫폼 저장소/런타임 공급자로 전달하고 로그·소스·예시 데이터에 포함하지 않는다. 회원 자료형에도 실제 사용자 정보를 하드코딩하지 않는다. 저장·만료·로그아웃 동작은 실제 서비스 계약에 맞춰 별도 구현한다.
